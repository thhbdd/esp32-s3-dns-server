# 内存与 Flash 预算（ESP32-S3 N16R8）

> 本文档由 AI 整理生成。

## 内部 SRAM（物理容量约 512 KB；实际可用堆依构建配置变化）

下面是历史预算示例，不是本次固件的 `idf.py size` 实测；编译优化和系统组件可能改变静态与动态占用。

| 用途 | 大小 | 说明 |
|---|---|---|
| Wi-Fi / lwIP 动态缓冲 | 60–100 KB | 取决于 RX/TX 缓冲数量和流量 |
| dns-rx ×2（v4/v6）、dns-up 线程栈 | 按任务创建栈大小计算 | 热点线程，必须在内部 RAM |
| DNS 服务器结构体 | ≈ 16 KB | 配置、限速表、上游状态 |
| L1 缓存 | 32 × ≈ 660 B ≈ 21 KB | 热门的小应答 |
| 规则匹配的热数据 | ≈ 15 KB / 镜像 | 块首键采样、单标签哈希表、后缀符号表 |
| 其他（事件循环、tcpip、定时器、主任务） | ≈ 25 KB | |

此版本的 `dc_thread_start` 以及 Web、订阅更新等任务使用**内部 DRAM 栈**；不能因为 XIP-from-PSRAM 就把 Flash 擦写/MMAP/TLS 路径所需的任务栈放到 PSRAM。Web 界面「概览 → 设备」中的「内部 RAM」显示当前剩余量和历史最低值，低于 30 KB 时就该减少 L1 缓存。

## PSRAM（8 MB）

| 用途 | 大小 | 说明 |
|---|---|---|
| 固件代码 + 只读数据（XIP） | ≈ 1.2 MB | 与固件大小相同 |
| 订阅规则镜像 | 实际镜像大小 | AdGuard DNS filter ≈ 2.4 MB；四个大列表合并 ≈ 3.5 MB；上限 4 MB |
| 响应缓存 L2 | 默认 2 MB | 可配置 0–4 MB |
| 待决表 + 等待者池 + ID 映射 | ≈ 150 + 220 + 128 KB | 最多 256 个并发上游查询、512 个等待客户端 |
| 查询日志 | 256 条 × 120 B ≈ 30 KB | 可配置 |
| 自定义规则镜像 | 通常 < 100 KB | |
| 规则编译（仅更新时） | 0.9 MB（AdGuard DNS filter）到 2.6 MB（四个大列表） | 编译结束即释放 |
| TLS 连接 | 每个 ≈ 30–40 KB | mbedTLS 动态缓冲 |

历史估算：1.2 MB 代码 + 2.4 MB 镜像 + 2 MB 缓存 + 0.6 MB 运行结构 + 0.9 MB 编译 ≈ 7.1 MB；但这**不是同时运行的可靠峰值证明**，内存碎片、实际可分配 PSRAM、TLS 并发与内部栈均可能导致分配失败。

规则重建时自动进入“编译内存模式”：释放 DNS 缓存 L2 环形缓冲区及索引、L1 热点表，期间 DNS 会继续走上游及现有过滤规则，但短暂没有缓存加速。结束后自动按最近一次设置恢复缓存尺寸。这里释放的是真实堆内存，不是仅清空缓存项。对于极大的合并列表，仍有可能因复杂规则、PSRAM 碎片、编译器索引或镜像切换所需空间导致内存不足；自动回收并非无限扩容。

切换镜像时现有实现会先通过 Flash 映射过渡，再加载 PSRAM 版本。如果过大的新镜像无法进入 PSRAM，订阅过滤可能暂时不可用并报错；因此大规模列表仍应逐步增量验证，并保留 OTA/串口恢复手段。

开机顺序是先加载规则镜像，再分配缓存，保证规则优先拿到内存。

## Flash（16 MB）

| 分区 | 偏移 | 大小 | 用途 |
|---|---|---|---|
| nvs | 0x9000 | 24 KB | 系统 NVS（PHY 校准） |
| otadata / phy_init | 0xF000 | 12 KB | |
| ota_0 / ota_1 | 0x20000 / 0x1A0000 | 1.5 MB ×2 | 固件 A/B（当前约 1.2 MB） |
| cfg | 0x320000 | 384 KB | 配置 JSON、自定义规则（≤ 96 KB）、本地解析（≤ 32 KB）、订阅状态 |
| rules_a / rules_b | 0x380000 / 0x780000 | 4 MB ×2 | 规则镜像 A/B |
| staging | 0xB80000 | 4.5 MB | 编译时的外部排序 run 存储 |

实测的 staging 峰值（`flc compile --staging`）：

| 列表组合 | 镜像 | staging 峰值 |
|---|---|---|
| AdGuard DNS filter | 2.37 MB | 2.24 MB |
| AdGuard DNS filter + AdAway | 2.60 MB | 2.30 MB |
| adblockdns 合并列表 | 2.62 MB | 2.61 MB |
| 以上全部 + EasyList | 3.49 MB | 3.3–4.0 MB（空间不足时原地压缩） |

**Flash 寿命**：旧版一次更新主要擦写镜像大小 + staging 峰值；v1.0.2 除此之外还会在成功提交后擦除约 8.5 MiB 的过时数据分区，因此 Flash 擦除工作量明显增加。Flash 擦写寿命取决于芯片规格、温度与擦写分布，无法据此直接承诺使用上百年。订阅内容没有变化时（条件请求返回 304）不会写 Flash。

## 真实运行时预算与统计解释

上表的数值属于设计预算或历史基线；不可把 IDE 显示的 Flash 文件大小、PSRAM 总容量、`heap_caps_get_free_size` 简单相加。应用编译器将常量/代码放入 PSRAM XIP 后，部分物理容量不再作为通用可分配堆展示；网络和 TLS 的栈、堆实际占用受请求并发和运行阶段影响。

当前 `dns_config_defaults` 对 ESP 平台设置 `cache_bytes=2 MiB`、`cache_l1=32`、`qlog_entries=256`、`tcp_workers=1`，与早期 64 项 L1、1000 条日志的预算表不同。务必以当前源码的默认值和设备状态页为准。

建议以一次启动、配置热点运行、STA 连接、DNS 高峰、更新订阅、TLS 握手、OTA 写入分别记录 **片内可用堆、片内最大连续块、PSRAM 空闲和最小空闲量**。这些诊断可以仅在开发构建中开启；发布构建无需新增周期性监控线程。

### 资源紧张时优先调整

1. **不能删掉的安全必需资源**：FreeRTOS 系统和 Wi-Fi DMA 所需的内部堆、Flash 操作期间必须有效的内部任务栈。
2. **可减少常驻开销**：DNS 查询日志条数、L1 条目数、L2 缓存大小、TCP 工作线程数、HTTP 同时连接数。
3. **按需分配**：证书未配置时不启动 DoH/DoT TLS 服务端；尽量只在执行订阅更新时分配编译工作区。
4. **不要牺牲 DNS 正确性**：削减 UDP/TCP 缓冲不能令大 EDNS/响应溢出；缓存缩水不应改变 TTL 语义。

### Flash 寿命不能按“每天一次 = 一百年”直接保证

NOR 擦写寿命、温度、磨损均衡与掉电次数取决于具体 Flash 芯片和写入实现。规则 A/B 与 staging 每次更新会擦写大量扇区；无变化时不重建能减小磨损，但不能对任意硬件承诺百年寿命。上线后应该记录规则实际更新频率与 Flash 错误率。

## 规则更新内存生命周期（v1.0.2，沿用 v1.0.1 的缓存方案）

1. ETag/Last-Modified 检查时不动缓存，以免无变化请求引发查询性能波动。
2. 真正需要编译才释放缓存：L1、L2 ring、索引全部回收；上游 DNS、当前生效的自定义规则和订阅规则不关闭。
3. 编译器的 chunk 大小为 **192 KiB**（以前为 512 KiB），降低 arena/offsets 的峰值；代价是更多的 Flash 外排序 run 和略大的镜像。233,248 行列表的测试结果：512 KiB 时镜像 2,737,416 字节，192 KiB 时 2,772,000 字节，staging 峰值由 2,740,224 增加至 2,809,856 字节。均低于 4MiB 镜像槽与 4.5MiB staging 预算；数值是 **Linux 主机实验**，不是设备性能测试。
4. 无论更新成功还是失败，缓存预算都会按最近一次 DNS 设置恢复，但原有缓存命中历史会丢失并重新积累。恢复时如 PSRAM 不足，已有缓存分配器仍可能回退到更小的实际容量；以设备显示的真实分配值为准。
5. 回收过时订阅状态数据；新镜像成功提交后物理擦除废弃规则槽位的全部 4 MiB 与 staging 的全部 4.5 MiB。借助清理完成标记避免无变化时反复擦除。这个选择会增加实际 Flash 擦除次数/磨损，但符合“不保留旧规则数据”的存储目标。


## v1.0.3 FSST 符号表内存修复

在更新过程中，旧版 FSST 符号表构建除了排序后的 192KiB 编译块，还需要三个同一时刻存在的数组：65,536 个哈希对（512KiB）、66,048 个候选符号（约 1,032KiB）、512 个单符号计数（2KiB），合计约 1.51MiB。该内存申请会发生在旧镜像仍然生效的时候，即使已释放 DNS 响应缓存也可能失败。

v1.0.3 将哈希表降至 8,192 项；FSST 训练三块数组合计约 202KiB。训练时遗漏某些哈希碰撞候选只会影响压缩率，不会影响规则匹配结果。若样本采集或符号表训练的内存申请依旧失败，编译器改用零符号表和原始后缀，规则不丢失，镜像可能增加且仍受 Flash 容量检查约束。内存数字描述的是 FSST 工作数组而非设备整体 PSRAM 峰值；最后仍须在 ESP32-S3 实机测量。
