# 订阅规则更新：内存回收、旧规则清理与 OTA

> 本文档由 AI 整理生成。

> 适用范围：ESP32-S3 N16R8，**本仓库 1.0.3**；保留原 `partitions.csv` 的 16MB Flash / 8MB PSRAM 分区布局。此文档面向设备使用者和二次开发者。

## 1. `compiler: out of memory (arena)` 是什么

这是**编译器工作堆内存申请失败**，不是 Flash `staging` 或 `rules_a/rules_b` 分区被划多导致的。编译时存在 `arena`、`offs`、正则和复杂规则索引、外排序临时缓冲等；而旧规则镜像、DNS 响应缓存仍在 PSRAM 中。编译器的 `arena` 或 `offs` 任一扩容失败都可能显示这个错误。

## 2. 这次改了什么

1. **仅在确定规则有变化、确实要重新编译时**释放 DNS 缓存。只是 HTTP 条件检查，没有变化则完全不碰当前缓存。
2. 开始编译前调用 `dns_server_cache_build_mode(..., true)`：底层锁住缓存、释放 PSRAM L2 环形缓冲和哈希索引、释放 L1 热缓存。不是只清空缓存条目，而是把底层堆内存归还。
3. DNS 解析继续接受请求、匹配当前生效规则、转发到上游；只是规则构建期间不命中 DNS 响应缓存，延迟和上游请求量可能暂时增加。
4. 编译完成或失败后必经 `dns_server_cache_build_mode(..., false)` 恢复。若用户在更新过程中修改了缓存容量，恢复**最新**设置，而不是更新前旧值。
5. 设备端 `chunk_bytes` 从 512KiB 降为 192KiB，减少单次 arena/offsets 扩容压力。代价是较多的 Flash 排序 runs、少量镜像膨胀及不同的写入耗时。
6. 更新前后做订阅列表签名检查。用户在下载过程中改变订阅时不会激活已过时的配置版本，会提示本轮失败并重新依据新配置更新。

缓存恢复后，**历史缓存条目不会复活**：这是为释放内存主动采取的取舍。若最新规则镜像非常大，实际 PSRAM 仍无法满足最新缓存预算，缓存分配器可能退回到更小容量。

## 3. 更换/删除订阅后旧文件怎样处理

当前实现不是每个 URL 一个持久文件：多个启用的订阅会被合并成**一个规则镜像**。下载只是在解析器中流过，`staging` 存临时排序 runs。修改 URL 或停用旧 URL 后：

- **更新成功**：新镜像仅含当前启用订阅，删除旧订阅状态（ETag、下载字节、旧报错等）并持久化。
- **持久化成功后，真正删除旧数据**：整个非活动规则分区（4 MiB）及 staging 编译临时分区（4.5 MiB）逐块擦除为 `0xFF`，而不是仅删除一个 4KiB 头部。当前有效规则分区绝不擦除。
- **更新失败**：不清理旧槽位，保留已提交的规则快照；如果在新镜像切换阶段内存不足，会尝试从旧槽恢复。
- **关闭所有订阅**：先持久化空订阅集合，再擦除 `rules_a`、`rules_b` 和 `staging` 三个分区中原有的规则数据。

**释放的是实际存储内容**：旧规则镜像和临时编译数据所在 Flash 扇区会被物理擦除。因为分区布局固定，这些空白扇区仍归属规则分区，可以被下一次更新复用，但不会扩容固件 OTA 分区；删除规则也不会自动增大 PSRAM。为了避免每次检查都重擦 Flash，在 NVS 的订阅状态中保存 `flash_gc_slot` / `flash_gc_gen` 完成标记；首次从旧版 OTA 后，即使列表未变化，也会清理历史遗留分区。

### 清理与容灾的权衡

完整擦除旧镜像之后，会失去“从前一个旧规则槽回退”的保护。如果新槽将来意外损坏，设备需要重新联网下载订阅。固件 OTA A/B 回滚和规则镜像 A/B 是**两套不同机制**；清理旧规则不清理旧固件。没有断电/掉电的实机测试前，不能保证全部极端断电窗口的行为。

## 4. 现有固件如何 OTA 升级

前提：旧固件 Web UI 正常、OTA 功能可用、Flash 分区仍是该仓库的 `partitions.csv`。本次**没有修改分区表、规则镜像格式、既有 NVS 字段或 OTA 分区偏移**，仅在订阅状态 JSON 中追加可忽略的清理完成标记，因此无需擦除整个 Flash。

Windows 的 ESP-IDF v6.1 PowerShell：

```powershell
cd D:\esp32-s3-dns-server
idf.py build
Get-Item .\build\esp32s3_dns.bin
```

编译成功后，将 **`build\esp32s3_dns.bin`** 上传至 Web UI 的 **系统 → OTA**。设备重启后再次打开 Web UI，确认固件版本为 `1.0.3`，检查 DNS 功能，随后执行一次过滤规则更新。旧 Wi-Fi 配置、手动 TLS 证书、黑白名单、当前有效过滤镜像和 DNS 监听参数应沿用现有配置。清理功能会在首次成功规则检查/更新时执行；Flash 物理擦除会增加写入时间和磨损，清理阶段不应反复断电。成功提交新镜像后缓存会先恢复，擦除工作再继续。

**不要上传** `build\merged-binary.bin` 或 `bootloader.bin`；这些是串口烧录用途。应用 OTA 分区只有 **1.5MiB**，最终以 `idf.py build` 的实际大小检查为准；如果镜像超限，应先优化镜像，而不是直接调整 `partitions.csv` 再 OTA。

## 6. `out of memory (symbol table)` 修复（v1.0.3）

此错误发生在 FSST 规则索引后缀压缩阶段。v1.0.2 在默认 192KiB 块编译的首次排序后，仍会额外一次分配 512KiB `pairs` 和 1,032KiB `cand`，因此缓存释放策略可能未能解决它。v1.0.3 将这部分哈希搜索空间限制为 8,192 项，FSST 临时数组合计约 202KiB；其余规则解析和查询逻辑不变。

如果分配仍失败，会使用没有符号压缩的合法镜像格式继续写入完整规则，**不会丢规则、不会跳过列表**，但 Flash 占用可能明显增加。单份 233,248 行样本，正常 v1.0.3 镜像为 2,772,000 字节；注入 FSST 内存失败后的退化镜像为 4,031,080 字节，仍未超过单个 4MiB 规则槽上限。若开启更多列表，总镜像可能超限，并按正常容量错误返回；它不是内存回收失败。

测试覆盖：主机 CTest 3/3、ASan/UBSan 3/3，模拟 FSST 内存失败后加载与查询，以及真实列表 10,003 个查询与旧镜像逐项比对。**没有在本环境完成 ESP-IDF v6.1 交叉编译或实机 PSRAM 峰值测试。**

升级时不更改 Flash 分区；编译生成 `build/esp32s3_dns.bin` 后核对固件应用描述符 `1.0.3`，再使用 Web UI OTA 上传应用固件（不要上传 `merged-binary.bin`）。
