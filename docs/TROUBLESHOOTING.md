# 常见故障排查手册

> 本文档由 AI 整理生成。

> 建议按照“硬件启动 → Wi-Fi → 服务监听 → DNS 查询 → 订阅 → TLS”的顺序排查。跳过前面的步骤往往会把内存分配失败误以为网络故障。

## 1. 192.168.4.1 能 ping 通但网页打不开

`ping` 只说明 Wi-Fi/网络协议栈能回应 ICMP，不意味着 HTTP 服务运行。请查看串口最初启动日志是否包含：

```text
E (...) dns: cannot start threads
E (...) web: web server failed to start on port 80
I (...) app: ... internal RAM free 6 KiB
```

这种情况下应优先怀疑**片内 SRAM / 任务栈分配不足**，而不是修改浏览器或重复擦写 Flash。历史版本曾因约 10 KB 的配置结构体局部栈拷贝击穿较小主任务栈；另外大型 Web/DNS 工作线程栈会消耗内存。当前修复版本已避免主要大结构体栈拷贝，但仍要实机核对。

排查命令：确保电脑连的就是 ESP32 SoftAP，并获得 `192.168.4.x` 地址；用 `curl -v http://192.168.4.1/` 检查连接是否拒绝/超时。若“连接被拒绝”，重点是 Web 服务未启动；若不通路由，则可能连接错 Wi-Fi 或设备重启。

## 2. ESP-ROM 重复打印、复位循环

根据第一条明确的异常类型区分：

| 串口信息 | 常见原因与方向 |
|---|---|
| `rst:0x1 POWERON` | 正常上电时可能出现 |
| `RTC_SW_CPU_RST` 连续出现 | 软件重启/断言/看门狗，需要查前一段栈回溯 |
| `free() target pointer is outside heap areas` | 指针损坏、栈溢出或双重释放，必须定位回溯地址 |
| `Cache error` / `s_task_stack_is_sane_when_cache_frozen` | Flash 操作期间使用 PSRAM 栈或访问缓存关闭的内存 |
| `Task watchdog got triggered` | 死锁、任务长时间占 CPU、不让出调度 |
| Wi-Fi 一直扫描/掉线 | 2.4 GHz、密码、AP 隔离、信号或 802.11 兼容性 |

诊断崩溃时保留从开机到**首次 backtrace** 的完整输出及与之匹配的 ELF 文件；不同构建的 ELF 地址不可直接混用。可用 `idf.py monitor` 或 `addr2line` 定位调用栈。任何 `abort()` 或堆断言都不应以“重启后可能恢复”处理。

## 3. Wi-Fi 热点正常，但连不上家用路由器

确认 2.4 GHz、SSID、密码正确；如果路由器启用了 WPA3-only、Wi-Fi 6 复杂选项或 MAC 过滤，先使用常规 WPA2-Personal 测试。静态 IP 必须属于可达子网，不与其他设备冲突；DHCP 模式需检查路由器地址池。先用路由器客户端列表找设备地址，不要猜测它还是 192.168.4.1。

## 4. DNS 查询没有应答

```bash
dig @设备IP example.com A
dig +tcp @设备IP example.com A
dig @设备IP example.com AAAA
```

- 首先检查 DNS UDP/53、TCP/53 是否监听，ESP32 Web 状态页的“连接正常”不代表 DNS 一定可用。
- 若管理服务可达而 DNS 不可达，查看 DNS 工作线程创建、端口绑定、ACL `local_only` 和本机防火墙。
- 若客户端经路由器转发，ESP32 看到的请求源可能是路由器，需检查允许网段设置。
- 如果所有外部域名都失败而本地记录正常，重点是上游 DNS、路由器网关、bootstrap/证书和网络出口。
- `SERVFAIL` 不是过滤拦截，通常意味着上游请求失败、超时或自身解析错误。

## 5. 规则下载失败或长期“未下载”

检查订阅 URL 是否实际可访问、设备是否获取网关和时间、HTTPS 信任链是否正常。部分托管在 GitHub Pages 的源在不同地区/运营商网络中可能不可达；可以暂时切换到可达的规则镜像源。下载 HTTP 错误页不得当作规则文件。错误信息应显示在订阅详情中；如果更新任务期间崩溃，则依旧需要串口日志，不应只看 Web 页面。

遇到“更新后规则消失”，检查是不是意外写入空镜像、强制重建失败覆盖旧槽或 Flash 分区越界；禁止通过格式化所有分区来掩盖问题。正确路径是先备份、定位失败阶段，再选择恢复旧镜像。

## 6. HTTPS DoH/DoT 无法连接

1. `GET /api/tls` 是否显示配置了证书且服务正在运行？
2. 客户端连接的域名是否出现在证书 SAN？服务器时间与证书有效期是否正确？
3. DoH 用 `https://.../dns-query`，不是 `http://.../dns-query`。
4. DoT TCP 853、HTTPS TCP 443 是否被路由器或防火墙阻止？
5. 是否使用了自签证书而客户端未信任？
6. DoH POST 是否带 `Content-Type: application/dns-message`，GET 是否正确 Base64URL 编码？
7. 设备 SRAM 是否足以分配 TLS 任务栈、握手缓冲和证书解析结构？

## 7. 运行时间一直是 0 小时 0 分

先观察前端是否只显示分钟（某些早期 UI 设计可能在第一分钟内固定显示零），再确认 `uptime` 统计是否持续增加。如果串口显示每隔几十秒崩溃重启，那么 uptime 回零是**重启的结果**，不是简单的 UI 错误。

## 8. DNS 解析“有时快有时慢”

先对比命中 L1/L2 缓存的局域网请求、未命中需外部上游的请求。不要把一次外部 DoH 的 TLS 新建连接时间计入本地规则匹配耗时。Wi-Fi 省电、2.4 GHz 干扰、丢包重试、TLS 握手、更新期间 Flash 擦写都会改变端到端 p99。建议用同一台有线测试主机、相同负载和固定测试时长复测。

## 9. OTA 升级后不能启动

首先确认 OTA 用的是应用固件 `.bin`，不是 0x0 合并镜像；固件大小不超过 1.5 MB 槽位；分区表没有变更。若仍无法启动，保留串口 Bootloader 选择 OTA 的日志与 app SHA256。不可因启动失败就重复整片 ERASE，可能失去回滚镜像和配置。
