# 性能测试（dnsbench）

> 本文档由 AI 整理生成。

`dnsbench` 是一个单文件、无依赖的 C 程序，用于在 Linux 上对 DNS 服务器做压力测试和延迟测量。

## 编译

```bash
cmake -S host -B build-host -DCMAKE_BUILD_TYPE=Release && cmake --build build-host -j --target dnsbench
# 或者
cc -O2 -pthread -o dnsbench tools/dnsbench/dnsbench.c -lm
```

## 两种负载模型

- **闭环**（`-c N`，默认）：始终保持 N 个查询在途，用于测**最大吞吐**。N 太小时测到的是 RTT 上限，N 太大时只会增加排队延迟。建议从 16、32、64 依次试。
- **开环**（`-r QPS`）：按固定速率发送，不等应答，用于测**某个负载下的延迟分布**和丢包。这种方式更接近真实网络，长尾延迟不会被「协调遗漏」掩盖。

## 场景

| 参数 | 测什么 |
|---|---|
| `--scenario cache` | 先把内置的约 100 个热门域名各查一次（预热），再循环查询，测的是**缓存命中路径** |
| `--scenario miss` | 每次查询 `随机10字符.dnsbench.invalid`，每次都要访问上游，测的是**上游转发路径** |
| `--scenario mixed --miss-pct 20` | 80% 热门域名 + 20% 随机名称 |
| `-f names.txt` | 自己的域名列表，每行 `域名 [类型]`；配合 `--random` 随机顺序，`--warmup` 预热 |
| `-t AAAA` / `-m A:70,AAAA:25,HTTPS:5` | 查询类型或类型比例 |
| `-e` / `--do` | 带 EDNS(0) / DNSSEC OK 位 |
| `--tcp [--tcp-conns N]` | DNS over TCP（持久连接 + 流水线） |

拦截路径可以用自己的列表测试：从规则里挑一些被拦截的域名放进 `-f` 文件。拦截应答完全在设备本地生成，速度与缓存命中相近。

## 排除上游的影响：假上游

`miss` 场景的结果受公网上游影响很大。要测设备**自身**的转发能力，可以让一台 Linux 机器当上游：

```bash
dnsbench --responder 0.0.0.0:5300 --delay 0      # 立即应答 A/AAAA，其余类型返回 NODATA
dnsbench --responder 0.0.0.0:5300 --delay 20     # 模拟 20 ms 的上游
```

然后在设备 Web 界面的「DNS 设置 → 上游」中填写 `192.168.1.x:5300`（Linux 机器的地址），再运行 `--scenario miss`。

## 输出

```
==== dnsbench summary: 192.168.1.53:53 (UDP) ====
duration          10.00 s
queries sent      ...
answers           ... (99.99%)
timeouts          ...
throughput        ... answers/s
rcodes            NOERROR ...  NXDOMAIN ...  SERVFAIL ...
latency (ms)      min ...  avg ...  max ...
percentiles (ms)  p50 ...  p90 ...  p95 ...  p99 ...  p99.9 ...
```

- `--histogram` 打印延迟分布，`--json` 输出机器可读的结果，`-i 1` 每秒打印一次进度。
- `-n 数量` 模式下，耗时算到最后一个应答为止（不含结尾等待超时的时间）；按 Ctrl-C 中断时，仍在途中的查询单独列为「unanswered」。
- `-e` 加 EDNS(0)（1232 字节），`--edns-size N` 指定其他大小；`--do` 设置 DNSSEC OK 位。
- 数值参数写错（例如 `-d abc`）或多出无法识别的参数时，dnsbench 直接报错退出，不会悄悄用默认值测试本机。
- `--responder 5300` 只写端口时监听所有地址。
- `--query 名称 [-t 类型]` 发一次查询并像 dig 一样打印应答，可用来检查拦截和重写是否生效。
- `tools/dnsbench/bench_suite.sh 设备IP` 会依次运行一整套标准场景，并把每个场景的 JSON 结果保存下来。

## 测试建议

1. 用**有线**连接的 Linux 主机，路由器和设备之间信号要好（RSSI 高于 -60 dBm）。Wi-Fi 空口通常是瓶颈，单个 2.4 GHz 链路的小包处理能力有限。
2. 先跑 `--scenario cache -c 1` 看单查询往返延迟，再逐步加大 `-c`，看吞吐什么时候不再增长、p99 什么时候明显变大。
3. 用开环 `-r` 在 50% 和 80% 最大吞吐下各跑 60 秒，记录 p99 和 p99.9。
4. 同时打开设备的「概览」页，或请求 `/metrics`，把设备内部的处理延迟（缓存 p50/p99）和 dnsbench 测到的端到端延迟对比，差值就是网络开销。

## 历史主机基线（不是本轮重测，更不代表设备性能）

下表来自旧版测试记录：Intel Xeon 2.8 GHz × 4 核、回环网络、`dnsd_host`（2 个 UDP 接收线程），加载 AdGuard DNS filter + AdAway（18.9 万个域名键），上游为本机 `dnsbench --responder`。**本轮没有重新运行这一套端到端压测，缺少同期原始机器日志时只能作为历史参考，不能作为当前版本性能证明。**

| 场景 | 结果 |
|---|---|
| 缓存命中，c=64，1 个发送线程 | 20.8 万 QPS，p50 0.24 ms，p99 1.0 ms（端到端） |
| 缓存命中，c=64，4 个发送线程 | 22.7 万 QPS |
| 服务器内部处理延迟（缓存命中） | p50 2 µs，p99 6 µs |
| 全部转发（miss），c=64 | 5.8 万 QPS，p50 0.97 ms |
| 混合 20% miss，开环 2 万 QPS | p50 0.07 ms，p99 0.40 ms，无超时 |
| TCP 流水线，4 个连接 | 4.5 万 QPS |
| 规则匹配（flc bench） | 平均约 2.5 µs/次 |

设备上的数据需要上板后用 dnsbench 实测。ESP32-S3 的 CPU 比测试主机慢一个数量级以上，Wi-Fi 空口也会限制小包速率，预计设备会受空口而不是 CPU 限制。

## 怎么公平比较 ESP32-S3 与其它 DNS 过滤器？

重点比较两个指标：**DNS 端到端时延**（从客户端发出请求到收到响应）和**设备内部处理时延**（不含网络往返）。两者不能互相代替：Wi-Fi 空口造成的抖动可能远大于一次 PSRAM 规则匹配。

对照测试至少需要以下四种固定负载：

1. **本地 A 重写**：无需上游，衡量 DNS 解析和构造应答。
2. **已拦截域名**：无需上游，衡量二进制过滤索引与响应。
3. **缓存命中**：分别使用热门小响应和包含大量记录的响应。
4. **缓存未命中**：固定同一个局域网假上游，测试重试/合并/队列，而不是混入公网不可控 RTT。

每种场景至少报告 QPS、p50/p90/p95/p99/p99.9、失败率、内部 SRAM 最低值、PSRAM 剩余、RSSI、测试时间和温度/供电情况。p50 减少几十微秒但 p99 升高几十毫秒，并不一定是好优化。

### 推荐实验矩阵

| 变量 | 建议测试值 | 想回答的问题 |
|---|---|---|
| 并发数 | 1、8、16、32 | 哪一点开始排队 |
| 目标 QPS | 50、100、200、500（以实际设备可持续能力调整） | p99 随负载如何变化 |
| 上游 | 假上游、局域网 DNS、公网 UDP、DoT、DoH | 网络/TLS 与规则时间如何区分 |
| 规则 | 空规则、普通域名 23 万条、复杂规则组合 | 规则索引是否造成明显额外延迟 |
| 缓存 | 关闭、512KiB、1MiB、2MiB | 命中率是否值得多占 PSRAM |
| Wi-Fi | RSSI 高/低、信道干扰 | 空口是否成为瓶颈 |
